## 1. Vendor Orders — Date Filters and Downloadable PDF

Enhance the Vendor Orders page with a date-filter dropdown containing:

- Recent Orders
- Last 1 Week
- Last 15 Days
- Last 30 Days
- Custom Date Range
- All Orders — display this option at the bottom of the dropdown.

Selecting an option must filter orders using their actual order placement date and time. Custom Date Range must allow the vendor to select a start date and end date.

Generate a downloadable, professionally formatted PDF containing the following information:

- Order date and time
- Order ID
- Customer name and available customer contact details
- Delivery address, where applicable
- Product names
- Product quantities and selling units
- Individual item prices
- Line-item totals
- Order subtotal, applicable fees and final order total, where available
- Order status
- Delivery status
- Vendor/store identification

The PDF must respect the selected date filter. For Custom Date Range, include only orders within the selected range.

**Access rules:**
- Each Vendor can download PDFs only for their own store's orders.
- Admin can download PDFs for any vendor/store and apply the same date filters.
- Admin should be able to identify the store and vendor associated with each order.
- Do not allow vendors to access another vendor's orders by changing URL parameters or API requests.

Follow the existing project’s currency, timezone, PDF-generation, and order-total conventions. Avoid recalculating financial values differently from the authoritative order records.

- All mandatory documents have been submitted.

Implement server-side enforcement, not just disabled buttons in the UI.

Bank account numbers and other sensitive details must be masked in normal display wherever appropriate. Only authorized Admin users may view the full details. Never include full bank details in logs, public APIs, customer responses, or PDFs.

## 4. Delivery Partner — Capture and Securely Store Order Photograph

Before a Delivery Partner picks up an order, provide a camera option to capture **one photograph of the complete order/package**.

The workflow must:
- Allow the partner to capture a photograph using a supported device camera.
- Show a preview and allow recapture before submission.
- Require the photograph before confirming pickup, unless an explicitly authorized exception mechanism already exists.
- Associate the photograph with the correct order, delivery assignment, partner, and capture time.
- Upload and store the image securely in the existing cloud storage architecture.
- Display the saved photograph to the assigned Delivery Partner and authorized Admin users.
- Allow Admin to inspect the photograph for security and operational oversight.
- Prevent customers, unrelated vendors, unrelated delivery partners, and unauthenticated users from accessing private image URLs.

Use private storage and authenticated access or short-lived signed URLs, as appropriate. Do not make the storage bucket public merely to simplify image display.

Handle camera permission denial, upload failure, retry, and poor network connectivity safely. Do not mark an order as picked up if the required photograph has not been securely saved.

Do not add product-by-product photography; one complete package photograph is sufficient.

## 5. Order Notifications and Vendor/Customer Order Workflow

### A. New order notification for Vendor

When a customer places an order, notify the correct Vendor.

When the Vendor portal is open, show an in-app popup/banner with a **View Order** action. Clicking it should open the relevant order details, including products, quantities, item prices, and order total.

The Vendor should be able to Accept or Reject the order from the relevant order view.

Keep the Vendor's main order actions conveniently accessible, using a sticky/fixed bottom action area where appropriate, so the Vendor does not need to scroll to the bottom of a long order page to accept the order or mark it ready.

Ensure sticky controls do not cover important content or conflict with mobile navigation.

### B. Background and closed-portal notifications

The user requires notifications to reach Vendors and eligible Delivery Partners even when their portals are in the background or closed.

Inspect the existing notification infrastructure first.

- Implement in-app notifications for active sessions.
- Use an existing supported push-notification mechanism if one is already configured.
- If background/closed-app notifications require additional push infrastructure, credentials, service-worker setup, platform configuration, or a paid provider, clearly identify the requirements and implement only the parts supported by the existing project without secrets or provider access.
- Do not claim that closed-app notifications work unless the complete mechanism is implemented and verified.
- Do not add OTP, SMS, WhatsApp, or paid services without explicit approval.
- Handle duplicate and delayed notifications safely. A notification must never cause the same order to be accepted or assigned twice.

### C. Customer-visible order statuses

The Customer portal must display these statuses in order:

Placed → Accepted → Preparing → Ready → Out for Delivery → Delivered

Rejected or cancelled orders must retain their appropriate separate terminal statuses and existing business rules.

Maintain valid transitions in the database and APIs. Do not merely change displayed labels while leaving the underlying workflow inconsistent.

### D. Simplified Vendor workflow

The Vendor must not have a separate manual **Preparing** action.

The intended Vendor workflow is:

1. New order notification appears.
2. Vendor opens the order and reviews the items and amounts.
3. Vendor Accepts or Rejects.
4. After accepting, the Vendor can proceed directly to the **Mark as Ready** action.
5. Mark as Ready updates the order to Ready for the Customer and initiates delivery-partner assignment/notification.

The Customer should still see the Preparing status between Accepted and Ready, even though the Vendor does not have to click a separate Preparing button.

Represent Preparing consistently in the backend, order history, or status projection using the existing architecture. Do not fabricate an event timestamp or claim a state transition occurred when it did not. Preserve a clear, auditable sequence of status changes.

Rejecting an order must follow existing authorization and stock-restoration rules.

### E. Delivery Partner assignment

When an order is marked Ready:
- Notify eligible Delivery Partners.
- Only active and eligible partners should be offered the delivery.
- The first eligible partner who successfully accepts the assignment must win.
- Implement assignment as an atomic server-side/database operation to prevent two partners from acquiring the same order during simultaneous acceptance.
- Losing partners should receive a clear response that the delivery is no longer available.
- Admin must be able to inspect the assignment and delivery history.

Preserve the existing delivery workflow and valid states, including acceptance, pickup, Out for Delivery, and Delivered. Pickup must enforce the required package-photo step.

Do not allow a partner to pick up or deliver an order assigned to someone else.
