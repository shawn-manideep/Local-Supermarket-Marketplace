==================================================
1. CUSTOMER PORTAL — CLOSED STORES MUST NOT ACCEPT ORDERS
==================================================

CURRENT REQUIREMENT:

If a Vendor/Store is closed, Customers must not be able to place an order from that store.

This must be enforced BOTH in the UI and server-side.

--------------------------------------------------
1.1 Customer UI
--------------------------------------------------

When a store is CLOSED:

Clearly show:

Store Closed

or:

Currently Closed

The customer may still be allowed to:

- View the store
- Browse products
- View product details
- View saved items/history

according to the existing application behavior.

However, the customer must NOT be able to successfully place a new order.

Disable or hide order-entry actions where appropriate, such as:

- Add to Cart
- Checkout
- Place Order

Use the existing product/store availability design.

Do not incorrectly mark individual products as out of stock merely because the store is closed.

--------------------------------------------------
1.2 Server-side enforcement
--------------------------------------------------

This is critical.

Do NOT rely only on disabling buttons.

When the customer attempts to create an order:

Backend must verify that the selected Vendor/Store is currently open/accepting orders.

If closed:

Reject the order with a clear structured error.

Example:

STORE_CLOSED

" This store is currently closed and cannot accept orders."

The existing order transaction must not:

- deduct stock
- create an order
- modify cart state
- create delivery records

when the store is closed.

--------------------------------------------------
1.3 Race-condition protection
--------------------------------------------------

The store-open check must happen as part of the existing order creation/checkout transaction or in a way that prevents:

Store is open
→ Customer starts checkout
→ Store closes
→ Order is still accepted

The final server-side order acceptance must verify current store orderability.

Reuse the existing transactional order architecture.

--------------------------------------------------
1.4 Vendor/Admin store status
--------------------------------------------------

Inspect the existing Vendor store status/open-close implementation.

Do not create a second store status system.

If the project already has:

- ACTIVE
- SUSPENDED
- PENDING_APPROVAL
- REJECTED

do not confuse those administrative statuses with daily operating hours/open/closed state.

Use the existing store-hours/open-close mechanism if already present.

If there is no proper orderability state, introduce the minimum required concept.

Add a product search field to the Vendor Catalog/Product Management page.

- Brand, if available

Do NOT expose products belonging to other Vendors.

Vendor A must only search:

- Vendor A's selected Master Catalog products
- Vendor A's Vendor-created products

--------------------------------------------------

Make the experience:

[ Search products by name or brand ]

Browse by Category

Both controls should remain visually consistent/equal width as already implemented.

Search and category filtering should work together.

Example:

Search = "Rice"
Category = "Grains"

Return only matching Vendor products.

--------------------------------------------------
2.3 Search behavior
--------------------------------------------------

Search should:

- be case-insensitive
- support partial matches
- handle empty search gracefully
- preserve existing product ordering
- work on desktop and mobile
- not expose internal product IDs unnecessarily

Do not create a completely separate search architecture if the existing API can be extended safely.

3. DELIVERY — INSTANT OR SCHEDULED DELIVERY
==================================================

We are introducing scheduled delivery.

At checkout, Customer should choose one of:

1. Instant Delivery
2. Scheduled Delivery

Example:

Delivery Option

○ Instant Delivery
  Deliver as soon as possible

○ Scheduled Delivery
  Choose a delivery time

--------------------------------------------------
3.1 Instant Delivery
--------------------------------------------------

When Customer selects:

Instant Delivery

Use the existing delivery workflow.

The order should proceed through:

PLACED
→ Vendor accepts
→ PREPARING
→ READY
→ Delivery Partner assignment
→ Pickup
→ OUT_FOR_DELIVERY
→ DELIVERED

Do not change the existing workflow unnecessarily.

--------------------------------------------------
3.2 Scheduled Delivery
--------------------------------------------------

When Customer selects:

Scheduled Delivery

Display available date/time options.

Example:

Delivery Date

[ Today ▼ ]

Delivery Time

[ 7:00 PM – 8:00 PM ▼ ]

The exact available slots must be based on the application's existing capabilities and Vendor/store operating hours.

Do NOT hard-code arbitrary slots without checking store availability.

--------------------------------------------------
3.3 Delivery slot design
--------------------------------------------------

Use a clear slot model.

For example:

Today
- 6:00 PM – 7:00 PM
- 7:00 PM – 8:00 PM
- 8:00 PM – 9:00 PM

Tomorrow
- 10:00 AM – 11:00 AM
- 11:00 AM – 12:00 PM
- 12:00 PM – 1:00 PM

The actual slot generation should respect:

- Store operating hours
- Store closed state
- Current time
- Existing delivery capabilities
- Existing delivery workflow

Do not offer slots that are already in the past.

--------------------------------------------------
3.4 Order snapshot
--------------------------------------------------

When the order is placed, save the selected delivery mode and scheduled slot as part of the order.

For example:

delivery_mode:
INSTANT

OR:

delivery_mode:
SCHEDULED

For scheduled orders also save:

scheduled_date
scheduled_start_time
scheduled_end_time

The selected values must become an order snapshot.

Changing store hours later must NOT silently change an already placed order's scheduled slot.

--------------------------------------------------
3.5 Vendor view
--------------------------------------------------

Vendor should clearly see the delivery mode on the order.

Example:

Delivery:

INSTANT

or:

SCHEDULED
08 Oct 2026
7:00 PM – 8:00 PM

Do not allow Vendor to accidentally change the customer's requested slot unless a future business rule explicitly supports rescheduling.

--------------------------------------------------
3.6 Delivery Partner view
--------------------------------------------------

Delivery Partner should also see:

Instant Delivery

or:

Scheduled Delivery
7:00 PM – 8:00 PM

The delivery assignment/workflow must continue to use the existing delivery architecture.

Do not create a second delivery system.

--------------------------------------------------
3.7 Scheduled delivery and order lifecycle
--------------------------------------------------

Do not automatically mark a scheduled order as OUT_FOR_DELIVERY before its scheduled time.

Respect the existing:

READY
→ PICKUP
→ OUT_FOR_DELIVERY
→ DELIVERED

workflow.

Define the minimum safe behavior based on the existing architecture.

If the existing Vendor/Delivery Partner workflow cannot yet enforce scheduled dispatch timing, report that clearly rather than inventing a complex scheduler.

4. VENDOR DOCUMENTS — ADMIN VERIFICATION
==================================================

CURRENT REQUIREMENT:

Vendor uploads required documents.

But uploading documents alone must NOT unlock the Vendor catalog.

Admin must verify and approve the documents first.

New onboarding flow:

Vendor logs in
↓
Documents required
↓
Vendor uploads mandatory documents
↓
Vendor submits documents for verification
↓
Admin reviews documents
↓
Admin approves
↓
Vendor catalog becomes accessible

--------------------------------------------------
4.1 Document states
--------------------------------------------------

Introduce a simple verification lifecycle.

Recommended states:

NOT_UPLOADED
UPLOADED / DRAFT
SUBMITTED
APPROVED
REJECTED

Use the existing Vendor Documents model where possible.

Do NOT create a duplicate document system.

--------------------------------------------------
4.2 Vendor document page
--------------------------------------------------

After uploading mandatory documents, show:

Mandatory Documents
4 / 4 uploaded

[ Submit for Verification ]

The Vendor must explicitly submit the documents for Admin review.

Before submission:

"Documents uploaded. Submit them for Admin verification."

After submission:

"Documents submitted for verification."

The Vendor should no longer be able to edit the submitted document without using an appropriate replacement/re-submission flow.

--------------------------------------------------
4.3 Catalog access rule
--------------------------------------------------

This is critical.

Vendor catalog access should depend on:

ALL mandatory documents
+
Admin approval

NOT simply upload completion.

Required logic:

Documents incomplete
→ Catalog LOCKED

Documents uploaded but not submitted
→ Catalog LOCKED

Documents submitted / under review
→ Catalog LOCKED

Documents rejected
→ Catalog LOCKED

Documents approved
→ Catalog UNLOCKED

Existing Vendors who already have access must NOT be unexpectedly locked out.

Treat existing approved/active Vendors as grandfathered unless the current architecture already has an explicit verification state for them.

--------------------------------------------------
4.4 Vendor UI
--------------------------------------------------

Show clear onboarding status.

Example:

Vendor Verification

Status:
⏳ Documents Under Review

Your documents have been submitted and are awaiting Admin verification.

Catalog access will be enabled after approval.

If rejected:

Status:
❌ Documents Rejected

Reason:
PAN Card image is unclear.

[Replace Document]
[Resubmit for Verification]

If approved:

Status:
✓ Documents Approved

Your account is verified.

[Go to Catalog]

--------------------------------------------------
5.1 Admin approval
--------------------------------------------------

Admin can approve the mandatory document submission.

When approved:

- Vendor verification status becomes APPROVED.
- Vendor catalog access becomes available.
- Vendor can add Master Catalog products.
- Vendor can create Vendor-specific products.

Do not automatically approve optional documents just because mandatory documents are approved.

Optional documents can remain informational unless the existing architecture requires separate verification.

--------------------------------------------------
5.2 Admin rejection
--------------------------------------------------

Admin must provide a rejection reason.

Example:

"PAN Card image is unclear."

The Vendor should be able to see the reason.

Vendor can replace the rejected document(s).

Vendor then submits again for verification.

Catalog remains locked until the new submission is approved.

--------------------------------------------------
5.3 Partial document rejection
--------------------------------------------------

Do not approve the Vendor if any mandatory document is rejected/missing.

Example:

FSSAI ✓
Aadhaar ✓
PAN ❌
Photo ✓

Overall status:

REJECTED / INCOMPLETE

Catalog remains locked.

The Vendor must correct the rejected/missing mandatory document and resubmit.
