## SOURCE OF TRUTH

The attached/available Master Product & Architecture Blueprint v1.1 is the authoritative architecture contract.

Use ONLY the v1.1 architecture decisions.

Do NOT use older versions of the blueprint or older project recommendations if they conflict with v1.1.

In particular, the following are LOCKED:

- Supabase PostgreSQL
- Drizzle ORM
- Zod
- Supabase Auth
- Roles: customer, vendor, admin
- No custom password authentication
- Store-owned independent products
- NO global/shared product entity
- NO `store_products` table
- Store-owned categories
- Vendor identity: 1 authenticated user : 1 store
- Admin signup: none
- Admin provisioning: manual
- Vendor isolation is mandatory
- Supabase Row-Level Security is required
- Vendor authorization must never trust store_id supplied by the client
- Customer resources must be scoped to the authenticated customer
- No delivery-partner system
- No payment gateway
- No marketplace UI implementation in this phase

# 4. AUTHENTICATED USER / ROLE MODEL

Use Supabase Auth as the authentication identity provider.

Application roles are:

customer
vendor
admin

Do not create custom password hashing/authentication.

Do not create a public role-assignment API.

Do not allow a client to assign itself the admin or vendor role.

The application database must link authenticated Supabase user IDs to the appropriate application profile/role.

The implementation must support:

- customer identity
- vendor identity
- admin identity

Vendor relationship:

ONE authenticated vendor user → ONE store.

Multi-staff vendor accounts are deferred.

---

# 5. ADMIN PROVISIONING

There is NO public admin signup.

Do not create:

POST /admin/register

Do not create any public API allowing arbitrary role assignment.

Admin accounts are manually provisioned.

Create the database/auth structure necessary for an administrator account to exist, but do not build an admin onboarding UI.

# 6. CUSTOMER PROFILE

Customer resources must later be scoped to that authenticated customer.

Do not implement customer-facing profile screens in this phase.

# 8. STORE DATABASE FOUNDATION

The stores table must support the architecture required by later phases.

Include the fields required for:

- store identity
- store name
- description
- logo/image reference where appropriate
- phone

Operating/open status will later be computed from operating hours.

Do not implement the store-management UI or API in this phase.

# 9. COMMISSION SOURCE

The store must support a nullable store-specific commission rate.

The intended rule is:

- if a store-specific commission rate exists, it is the effective rate
- otherwise a future platform default commission rate may be used

Do NOT create automated settlements.

Do NOT create vendor settlement tables.

Do NOT implement commission calculations in checkout yet.

The database must simply preserve the source configuration needed by later phases.

# 12. STORE-OWNED CATEGORIES

Categories belong to exactly one store.

There is NO global category master.

A category cannot be shared between stores.

Create the database relationship:

store
  ↓
category
  ↓
products

Do not implement category management UI/API yet.

---

# 13. STORE-OWNED PRODUCTS — CRITICAL

Each product belongs to exactly ONE store.

Each product may belong to one store-owned category.

Required conceptual product fields:

id
store_id
category_id
name
description
sku
external_code
price
availability
stock_quantity
image_url
created_at
updated_at

`sku` and `external_code` may be nullable initially.

Product names must NOT be global unique identifiers.

Products with the same name in different stores must be allowed.

DO NOT create:

global product
global_products
store_products

There must be NO global/shared product catalog.

This is a locked architectural decision.

---

# 14. SOFT DELETE / ACTIVE FLAGS

Products and categories must not be hard-deleted casually once historical references can exist.

Use an `is_active` flag for products and categories.

Meaning:

is_active = true
→ active catalog entity

is_active = false
→ disabled/discontinued and not customer-facing

For products, availability is separate:

availability = true
→ active product currently available for ordering

availability = false
→ active product temporarily unavailable/out of stock

Do not confuse:

is_active

with:

availability

Do not physically delete historical order information.

# 20. SUPABASE ROW-LEVEL SECURITY

Enable RLS on application tables where appropriate.

RLS must provide a second security layer beneath the backend.

At minimum establish the architecture needed to enforce:

### Customer isolation

A customer must only access their own customer-owned resources.

### Vendor isolation

A vendor must only access resources belonging to their authorized store.

Vendor A must never be able to access Vendor B's:

- store
- categories
- products
- service pincodes
- orders
- operational data

### Admin access

Admin access must be role-controlled.

Do not create a public policy that allows arbitrary authenticated users to become admins.

Document the RLS design clearly.
