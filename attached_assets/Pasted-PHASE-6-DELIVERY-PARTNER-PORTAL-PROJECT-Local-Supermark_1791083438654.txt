PHASE 6 — DELIVERY PARTNER PORTAL

PROJECT:
Local Supermarket Marketplace

OBJECTIVE:
Introduce a dedicated Delivery Partner role and portal into the existing marketplace architecture.

The target business flow is:

Customer
   ↓
Order
   ↓
Vendor
   ↓
Delivery Partner
   ↓
Customer

Phase 6 is ONLY the Delivery Partner identity, authentication, profile, authorization, dashboard foundation, and portal UI.

DO NOT implement the actual delivery assignment or delivery execution workflow yet.

That will be Phase 7.

--------------------------------------------------
1. IMPORTANT SCOPE BOUNDARY
--------------------------------------------------

IMPLEMENT IN THIS PHASE:

- Delivery Partner role
- Delivery Partner account/profile
- Username/password login
- Partner authentication
- Partner authorization
- Partner active/inactive state
- Delivery Partner portal
- Partner dashboard
- Partner order/duty data structures required for the portal
- Basic pending/assigned/completed/cancelled/rejected views where supported
- Secure partner-only API access
- Partner navigation and logout
- Foundation required for Phase 7

DO NOT IMPLEMENT IN THIS PHASE:

- Vendor → Delivery Partner assignment
- Automatic delivery assignment
- Delivery Partner accepting/rejecting a duty
- Pickup workflow
- OUT_FOR_DELIVERY transition
- DELIVERED transition
- Delivery notifications
- Delivery partner location tracking
- GPS
- Maps
- Route optimization
- External SMS
- WhatsApp notifications
- Push notification infrastructure
- Payment changes
- Customer delivery UI redesign
- Vendor order workflow redesign
- Stock logic changes
- Master Catalog changes
- Reorder changes

Do not start Phase 7.

--------------------------------------------------
2. PRESERVE CURRENT ARCHITECTURE
--------------------------------------------------

The current marketplace already contains:

- Customer authentication
- Vendor authentication
- Admin authentication
- Role-based authorization
- Stores
- Orders
- Order items
- Order status history
- Product variants
- Stock management
- Master Catalog
- Vendor order management

Do not replace the existing authentication architecture.

Do not create a second authentication system.

Extend the existing role-based architecture cleanly.

Supabase Auth remains responsible for:

- password authentication
- sessions
- tokens
- authenticated user identity

Application database records remain responsible for:

- application role
- partner profile
- partner status
- partner-specific business data

--------------------------------------------------
3. DELIVERY PARTNER ROLE
--------------------------------------------------

Introduce a new application role:

DELIVERY_PARTNER

The role must be distinct from:

- CUSTOMER
- VENDOR
- ADMIN

Do not reuse VENDOR or CUSTOMER permissions.

Role authorization must be enforced server-side.

Never trust a client-provided role.

The authenticated user's server-side role must determine access.

--------------------------------------------------
4. DELIVERY PARTNER ACCOUNT
--------------------------------------------------

A Delivery Partner account should contain at minimum:

- user identity
- username
- active/inactive status
- partner profile
- display name
- mobile/contact information if the existing architecture supports it
- created_at
- updated_at

Do not store a plaintext password in the application database.

Passwords must continue to be handled by Supabase Auth.

--------------------------------------------------
5. ACCOUNT CREATION
--------------------------------------------------

Delivery Partner accounts are NOT customer self-registration accounts.

For Phase 6, partner accounts should be provisioned through an authorized administrative workflow.

Use the existing admin authorization model.

Admin should be able to create/provision a Delivery Partner account with:

- Username
- Password
- Display Name
- Contact Number if supported
- Active/Inactive status

Do not create public "Sign up as Delivery Partner".

Do not allow customers to change their own role to DELIVERY_PARTNER.

Do not allow vendors to change their own role.

Do not expose partner provisioning to customers.

--------------------------------------------------
6. USERNAME RULES
--------------------------------------------------

Reuse the existing username architecture/rules already approved for the marketplace.

Do not create a different username format for Delivery Partners.

Username must be:

- globally unique
- case-insensitive for uniqueness
- normalized consistently
- validated server-side

Do not create a separate partner username namespace.

Do not allow duplicate usernames across:

- customers
- vendors
- admins where applicable
- delivery partners

--------------------------------------------------
7. LOGIN
--------------------------------------------------

Delivery Partner login must use:

Username
+
Password

Do not require Gmail/email as the login identifier.

Do not require phone number as the login identifier.

After successful login:

- establish the existing authenticated session
- resolve the application role
- verify DELIVERY_PARTNER role
- load partner profile/status
- route to Delivery Partner Portal

Inactive partners must NOT be allowed to access partner functionality.

Use the existing session/logout architecture.

--------------------------------------------------
8. ACTIVE / INACTIVE STATUS
--------------------------------------------------

Delivery Partner must have a clear status:

ACTIVE
INACTIVE

ACTIVE:
- can log in
- can access partner portal
- can later receive delivery assignments in Phase 7

INACTIVE:
- cannot access partner functionality
- existing session must be denied/invalidated at protected API boundaries
- should receive a clear inactive-account message

Do not delete inactive partner records.

Historical delivery information must remain associated with the partner.

--------------------------------------------------
9. DELIVERY PARTNER PROFILE
--------------------------------------------------

Create the smallest appropriate partner profile structure.

Recommended conceptual model:

delivery_partner_profile

Fields should include only information actually needed now.

For example:

- id
- user_id
- display_name
- contact_number if supported
- status
- created_at
- updated_at

Do not add unnecessary fields such as:

- vehicle tracking
- GPS coordinates
- route
- driver license metadata
- bank details
- payout configuration
- live availability engine

Those are outside Phase 6.

--------------------------------------------------
10. DELIVERY PARTNER PORTAL
--------------------------------------------------

Create a dedicated portal for DELIVERY_PARTNER users.

The portal must NOT look like the Vendor dashboard.

Use a simple delivery-focused layout.

Suggested navigation:

Dashboard
My Deliveries
Profile
Logout

Do not show:

- Vendor catalog
- Master Catalog
- Vendor orders
- Vendor stock
- Customer management
- Admin controls

--------------------------------------------------

Dashboard should provide a simple operational summary.

Suggested sections:

TODAY'S DELIVERIES

- Pending
- Assigned
- In Progress
- Completed

Do not create fake delivery records.

Do not generate sample assignments in the database.

--------------------------------------------------
12. MY DELIVERIES
--------------------------------------------------

Create the foundation for a "My Deliveries" page.

It should support the future delivery workflow but must not execute Phase 7 actions yet.

Possible states:

- Pending
- Assigned
- Pickup Pending
- Out for Delivery
- Delivered
- Cancelled
- Rejected

However, do NOT add buttons such as:

- Accept Duty
- Reject Duty
- Pickup
- Start Delivery
- Mark Delivered

Those belong to Phase 7.

For now the page may show:

"No deliveries assigned yet."

This is acceptable.

--------------------------------------------------
13. DELIVERY DATA MODEL
--------------------------------------------------

Before adding a new table:

INSPECT the existing schema.

Determine whether an existing delivery/order structure can safely support the Phase 6 foundation.

Do not create duplicate delivery concepts.

The target relationship for Phase 7 is:

order
→ delivery assignment
→ delivery partner

If the current schema does not contain a suitable assignment structure, create the smallest additive structure needed for Phase 7 readiness.

A future assignment should conceptually identify:

- order
- delivery partner
- assignment status
- timestamps

But do NOT implement assignment behavior yet.

Do not create:

- routing tables
- tracking tables
- location history
- notification queues

unless absolutely required by existing architecture.

--------------------------------------------------
14. PARTNER ORDER VISIBILITY
--------------------------------------------------

IMPORTANT SECURITY RULE:

A Delivery Partner must NOT automatically gain access to all marketplace orders.

Partner order visibility must eventually be assignment-based.

For Phase 6, since assignment is not implemented yet:

- partner may see zero assigned deliveries
- partner may see only their own partner profile
- partner must not see arbitrary vendor/customer orders

Do not expose all READY orders to every partner.

Do not expose all customer information globally.

--------------------------------------------------
15. CUSTOMER DATA PRIVACY
--------------------------------------------------

When delivery assignment is eventually implemented, the partner will need fulfillment information.

For Phase 6, do not expose customer information unnecessarily.

Do not create a general customer directory for delivery partners.

Do not expose:

- customer password
- customer authentication data
- payment credentials
- unrelated customer orders
- internal vendor data

Only assignment-specific fulfillment information should be exposed later.

--------------------------------------------------
16. PARTNER AUTHORIZATION
--------------------------------------------------

Create server-side authorization helpers/middleware for:

requireDeliveryPartner

and use it on all partner APIs.

Examples:

GET /api/delivery-partner/me
GET /api/delivery-partner/dashboard
GET /api/delivery-partner/deliveries

Exact route names may follow existing project conventions.

Do not allow:

CUSTOMER → partner endpoints
VENDOR → partner endpoints
ADMIN → partner operational endpoints unless explicitly authorized

Admin may have administrative access where appropriate.

--------------------------------------------------
17. PARTNER API
--------------------------------------------------

Create minimal APIs required for Phase 6.

At minimum:

GET current partner profile

GET partner dashboard summary

GET partner's own deliveries/assignments

The deliveries response may legitimately return:

[]

until Phase 7 assignment functionality exists.

All APIs must:

- require authentication
- require DELIVERY_PARTNER role
- verify partner status
- scope records to authenticated partner identity

Never accept arbitrary partnerId from the client as the authorization source.

If an endpoint accepts partnerId for administrative purposes, independently authorize it.

--------------------------------------------------
18. PROFILE
--------------------------------------------------

Provide a simple partner profile page.

Display:

- Display Name
- Username
- Contact Number if available
- Account Status

Do not allow the partner to change:

- role
- status
- username if username is immutable under the existing architecture

If profile editing already has an established safe pattern, only allow appropriate profile fields.

--------------------------------------------------
19. LOGOUT
--------------------------------------------------

Use the existing logout/session clearing implementation.

After logout:

- partner cannot access protected pages using browser back
- partner APIs must reject unauthenticated requests
- cached partner data must not remain visible to another account

Follow the same account-switching/session-clearing protections already established in the customer/vendor portals.
