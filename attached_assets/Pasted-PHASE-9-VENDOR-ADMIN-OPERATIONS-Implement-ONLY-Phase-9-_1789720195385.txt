1. PHASE 9 OBJECTIVE
==================================================

==================================================
2. VENDOR SCOPE
==================================================

Vendor is authenticated using the existing Supabase Auth architecture.

Vendor identity must resolve to exactly one store in the MVP.

Never trust a client-provided store_id for authorization.

Every vendor operation must derive:

authenticated vendor
    ↓
vendor user identity
    ↓
owned store
    ↓
store_id
    ↓
authorized query

Vendor must NEVER access another store's data.

==================================================
3. VENDOR ORDER DASHBOARD
==================================================

Implement the vendor order-management dashboard.

The vendor should be able to:

- view incoming orders
- view order details
- see current order status
- accept PLACED orders
- reject PLACED orders
- move accepted orders to PREPARING
- move preparing orders to READY
- move ready orders to OUT_FOR_DELIVERY
- mark out-for-delivery orders as DELIVERED

Use the existing Phase 8 lifecycle rules.

Do NOT create arbitrary status editing.

==================================================
4. LEGAL STATUS TRANSITIONS
==================================================

Preserve exactly:

PLACED → ACCEPTED
PLACED → REJECTED
ACCEPTED → PREPARING
PREPARING → READY
READY → OUT_FOR_DELIVERY
OUT_FOR_DELIVERY → DELIVERED

Customer cancellation remains:

PLACED → CANCELLED

Do not modify these rules.

Do not allow:

PLACED → PREPARING
PLACED → READY
PLACED → DELIVERED
ACCEPTED → DELIVERED
DELIVERED → PREPARING
REJECTED → ACCEPTED
CANCELLED → ACCEPTED
etc.

The existing lifecycle service should remain the authoritative state machine.

9. STATUS HISTORY
==================================================

Do NOT directly update order status from the dashboard.

- lock the order
- verify current status
- verify legal transition
- update status
- append status history
- commit transactionally

Do not duplicate this logic in the frontend.

==================================================
10. CONCURRENCY
==================================================

The dashboard must handle concurrent changes safely.

Example:

Vendor A opens an order showing:

PLACED

Another valid actor changes it to:

ACCEPTED

Vendor A then clicks Reject.

The backend must reject the stale/illegal transition.

The frontend should refresh the order and display the current status.

Never let stale UI state bypass backend lifecycle protection.
