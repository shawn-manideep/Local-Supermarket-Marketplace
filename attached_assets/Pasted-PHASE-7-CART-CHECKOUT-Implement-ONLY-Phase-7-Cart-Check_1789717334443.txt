==================================================
2. LOCKED ONE-CART RULE
==================================================

The architecture requires:

ONE CART = ONE SUPERMARKET

A customer can have an ACTIVE cart for a store.

A cart contains products from exactly one store.

Example:

Customer A
  ↓
Store A
  ↓
ACTIVE cart
  ├── Product A
  └── Product B

The cart must never contain:

Product A from Store A
+
Product B from Store B

Reject any cross-store cart manipulation.

==================================================
3. CART LIFECYCLE
==================================================

Existing cart statuses:

- ACTIVE
- ABANDONED
- CONVERTED

Preserve these statuses.

Do not invent additional cart statuses.

When the customer changes supermarket:

Existing Store A ACTIVE cart
        ↓
Customer chooses Store B
        ↓
Store A cart becomes ABANDONED
        ↓
Store B cart becomes ACTIVE when an item is added

Do NOT delete the old cart.

Historical cart records should remain available according to the existing architecture.

Do not physically delete carts merely because the customer changes stores.

==================================================
4. ONE ACTIVE CART PER STORE
==================================================

The Phase 2 schema contains the rule for one active cart per customer/store.

Preserve the existing database constraint.

Do not create multiple active carts for the same:

customer + store

If concurrent requests could create duplicate active carts, use a safe database transaction/upsert/constraint-driven approach.

Do not rely only on frontend state.

==================================================
5. CUSTOMER CART OWNERSHIP
==================================================

Every cart operation must derive the customer identity from the authenticated Supabase session.

NEVER trust:

- customer_id
- owner ID
- arbitrary cart owner
- role

from the request body.

Example:

Authenticated Customer A
       ↓
Customer A identity
       ↓
Customer A carts

Customer A must never be able to access Customer B's cart by changing:

cartId
customerId
storeId

in a request.

Return appropriate not-found/authorization responses without leaking another customer's cart.

==================================================
6. CART STORE OWNERSHIP
==================================================

A cart belongs to exactly one store.

Every cart item must belong to a product from the same store.

When adding a product:

1. Authenticate customer.
2. Resolve customer identity.
3. Verify product exists.
4. Verify product belongs to an eligible store.
5. Verify product is active.
6. Verify product is available.
7. Resolve product's store.
8. Locate/create the customer's active cart for that store.
9. Add/increment the cart item.

Never accept a client-provided store_id as the source of truth.

The product's database relationship determines its store.

==================================================
7. ADD TO CART
==================================================

Implement the backend operation to add a product to the cart.

Input should be minimal, for example:

- productId
- quantity

Do not accept client-supplied:

- price
- subtotal
- total
- store_id
- product name
- commission
- delivery fee

The backend derives these values.

Validate:

- productId is a valid UUID
- quantity is a positive integer
- quantity is within a reasonable safe bound
- product is active
- product is available
- product belongs to an eligible store
- customer has access to that store

Do not implement negative quantities.

Do not allow zero quantity as an add-to-cart operation.

==================================================
11. CART PRICE
==================================================

The cart must derive price from the current product record.

The client must NEVER be allowed to submit a price.

Example malicious request:

{
  "productId": "...",
  "quantity": 2,
  "price": 1
}

The backend must ignore/reject the client price.

The server calculates:

line subtotal =
current product price × quantity

Cart subtotal =
sum of line subtotals

Do not introduce discounts.

18. STORE SWITCHING
==================================================

Backend detects existing active cart for another store.

Return a structured response indicating:

- existing cart store
- requested store
- store switch required

The UI should then ask for confirmation:

"Your cart contains items from another supermarket. Start a new cart for this supermarket?"

If the customer confirms:

1. Mark existing Store A cart as ABANDONED.
2. Create/reuse an ACTIVE Store B cart.
3. Add the requested Store B item.

Do not silently destroy the old cart.

Do not delete it.

Do not merge products from two stores.
