# Local Basket — Mobile Number and Password Registration

Update the new-account registration forms to align with the mobile-number login experience already implemented.

## 1. Customer Sign Up

Update the Customer registration form to include:
- Mobile Number
- Password
- Confirm Password

Requirements:
- Remove the email field from the visible Customer registration form.
- Validate Indian mobile numbers consistently with the existing login implementation, accepting 10 digits or a +91 prefix.
- Validate password strength and confirm that both password fields match.
- Associate the new account with the correct Customer role.
- Require secure mobile-number ownership verification before treating the number as a verified login identity.
- Do not create duplicate accounts for an existing mobile number.
- Preserve the existing Customer profile, session, and authorization architecture.

## 2. Vendor Sign Up

Update the Vendor registration form to include:
- Shop Name
- Mobile Number
- Password
- Confirm Password

Requirements:
- Remove the email field from the visible Vendor registration form.
- Use the same mobile-number normalization and password validation as Customer registration.
- Associate the account with the correct Vendor identity and store profile.
- Preserve Admin approval, required document verification, suspension rules, and catalog-access restrictions.
- New Vendors must not receive automatic approval.
- Require secure mobile-number ownership verification before trusting the number for login.
- Prevent duplicate mobile-number and account creation.

## 3. Authentication Architecture — Mandatory Inspection

Before implementing, inspect the existing Supabase Auth setup and the recently implemented mobile-number login flow.

The current registration flow may depend on Supabase email/password authentication, email-based recovery, or email confirmation. Do not assume removing the email field from the UI is sufficient.

Determine the safest compatible way to create Customer and Vendor accounts with mobile number and password while preserving the existing Auth UUIDs, roles, profiles, and account status.

Do not create fake email addresses, silently mark phone numbers verified, create replacement accounts, or bypass Supabase Auth.

If the existing architecture requires a verified phone enrollment step or provider configuration before password-based registration can work without email, report the limitation and implement only the safe portion that can be completed without provider setup.

## 4. Existing Users and Other Portals

- Preserve existing Customer and Vendor accounts and legacy sign-in.
- Do not change Delivery Partner provisioning; it remains Admin-only.
- Do not change Admin login or recovery.
- Do not enable WhatsApp OTP or SMS authentication as part of this task.
- Do not modify existing phone verification status or substitute contact/address/order numbers for login identities.

## 5. Tests and Acceptance Criteria

Verify:
1. Customer registration shows Mobile Number, Password, and Confirm Password, without an email input.
2. Vendor registration shows Shop Name, Mobile Number, Password, and Confirm Password, without an email input.
3. Validation rejects invalid numbers, weak passwords, and mismatched confirmation.
4. Account creation preserves correct roles and existing authorization rules.
5. Duplicate or unverified mobile numbers cannot bypass identity checks.
6. Existing accounts and legacy login continue working.
7. Admin and Delivery Partner authentication/provisioning remain unchanged.

Run the relevant tests, typechecks, and builds. Do not run automated browser tests; I will test manually.

Do not deploy, modify production settings, configure paid providers, or make unrelated changes.

At completion, report the files changed, whether email-free registration is fully supported by the current Supabase configuration, any required manual verification steps, and test results. Stop for manual verification.
