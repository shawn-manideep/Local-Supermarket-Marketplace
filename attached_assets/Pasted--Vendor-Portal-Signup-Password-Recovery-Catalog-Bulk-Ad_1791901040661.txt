# Vendor Portal — Signup, Password Recovery, Catalog Bulk Add, Inline Variants and Session Persistence

Implement the following corrections in the existing Local Supermarket Marketplace. Inspect the current Vendor Portal, authentication flow, catalog components, variant editor, routing and session management before modifying code.

Do not redesign the application or modify Customer, Delivery Partner or Admin functionality.

## 1. Add Vendor Signup for New Accounts

Currently, the Vendor Portal does not show an option to sign up for a new account.

Requirements:
- Add a visible **Create Account / Sign Up** option on the Vendor login screen.
- Reuse the existing Vendor registration flow and backend APIs if available.
- Collect the required vendor and account details according to the existing registration requirements.
- Provide password and confirm-password fields with validation.
- Ensure duplicate usernames or other existing unique identifiers are handled with clear messages.
- Preserve existing vendor approval and document-verification requirements.
- A newly registered Vendor must not bypass Admin approval or any existing catalog-access restrictions.
- Do not create a second authentication system or weaken existing authorization.

If Vendor registration is intentionally restricted by the current architecture, identify the restriction and implement the smallest safe registration flow consistent with the existing rules.

## 2. Correct Forgot Password / Password Recovery

The current Vendor Forgot Password flow asks for an email address, but the desired experience is to let the Vendor enter a new password and confirm it.

Important: Do not allow anyone to reset an account's password merely by entering a new password without verifying ownership.

Inspect the existing authentication provider and supported recovery APIs.

Implement the correct secure flow:
- If the existing system supports a verified recovery link or authenticated password reset, use it.
- After the account owner has been verified, show **New Password** and **Confirm New Password** fields.
- Validate that both passwords match and meet the existing password policy.
- Save the new password through the supported authentication mechanism.
- Show a success message and allow the Vendor to sign in with the new password.

Do not ask for an email address on the final new-password screen when a verified recovery session already exists.

If the existing system requires an email or other identifier to initiate recovery, retain that initial verification step. Do not bypass it or invent a password-reset API.

## 3. Add “Add All Products” in the Vendor Catalog

Add a convenient bulk action to the existing Vendor Catalog/Master Catalog screen so a Vendor can add multiple available Master Catalog products to their store at once.

Requirements:
- Add an **Add All Products** action where it is contextually appropriate.
- Allow the Vendor to select all eligible products, preferably with a selection checkbox and a bulk-add action.
- Show the number of eligible products selected.
- Prevent duplicate store listings.
- Skip products already present in the Vendor's store and report them clearly.
- Respect the existing vendor-local product and variant model.
- Do not automatically create global Master Catalog products.
- Do not invent default prices, stock quantities, selling units or pack sizes.
- If adding a Master Catalog product requires vendor-specific price, stock or variant information, allow the Vendor to provide the required information before saving.
- Provide a confirmation step showing how many products will be added.
- Process the operation safely and report successes, skipped products and failures.
- Prevent repeated clicks from creating duplicate listings.
- Keep other vendors' catalogs and listings completely isolated.

If “Add All Products” cannot safely create complete listings without required vendor information, implement **Select All Eligible → Add Selected** and clearly identify the remaining information needed.

## 4. Show Product Variants Inline Instead of Scrolling to the Bottom

Currently, selecting a product from the Master Catalog redirects or scrolls the page down to the variant editor. The Vendor should be able to expand the product and manage its variants directly underneath that product.

Required behavior:
- When the Vendor selects or expands a Master Catalog product, show its existing vendor-specific variant editor directly below that product row/card.
- Use an inline expandable/collapsible section or dropdown-style panel.
- Keep the selected product visible; do not automatically scroll to the bottom of the page.
- Allow the Vendor to add, edit and remove variants according to the existing business rules.
- Preserve existing variant identifiers, selling units, pack sizes, price and stock behavior.
- Maintain unsaved edits when expanding or collapsing other product rows where practical.
- Make the inline editor usable on mobile and desktop.
- Avoid rendering duplicate variant editors for the same product.
- Do not introduce Master Catalog variants if the current architecture stores selling variants at the vendor-listing level.

## 5. Fix Unexpected Vendor Sign-Out When Switching Tabs

This is the highest-priority bug.

Currently, switching between Vendor Portal tabs causes the Vendor to be signed out unexpectedly.

Inspect:
- Authentication/session provider lifecycle.
- Vendor portal routing and tab state.
- Supabase session persistence and auth-state listeners.
- Effects that trigger sign-out or clear session state during navigation.
- Component keys and conditional rendering that may remount the authenticated portal.
- API 401 handling and any global unauthorized-response logic.
- Browser refresh and session hydration behavior.

Fix the actual root cause rather than masking the symptom.

Required behavior:
- Switching between Vendor tabs must not sign the Vendor out.
- Vendor session must remain valid during normal navigation and component rerenders.
- Returning to the previous tab must preserve the authenticated Vendor and its permitted screen state where appropriate.
- Refreshing the page must restore the session when the underlying authentication provider supports persistence.
- A genuine logout, expired session or revoked account must still require authentication.
- Vendor authorization, account isolation, Admin approval and document-verification restrictions must remain enforced.
- Do not weaken authentication, ignore 401 responses globally, or store passwords or access tokens insecurely.
- Do not change Customer, Delivery Partner or Admin session behavior.
