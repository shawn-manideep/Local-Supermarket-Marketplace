# Local Basket — Vendor Signup, Password Reset and Application Logo Management

Implement the following enhancements in the existing Local Basket project. First inspect the current authentication flows, role permissions, Admin portal, application settings, and branding components. Reuse the existing architecture wherever possible. Do not rebuild working features or modify unrelated modules.

## 1. Vendor Portal — New Vendor Sign Up

Add a clearly visible **“Sign Up as Vendor”** option on the Vendor Login screen.

### Registration form
Include:
- Shop Name
- Username
- Password
- Confirm Password
- Required validation and clear error messages

### Requirements
- Allow new vendors to create an account through the registration flow.
- Enforce the existing global username uniqueness rules, case-insensitively.
- Validate password and confirm password before submission.
- Use the existing Supabase Auth and backend authentication architecture. Never store plaintext passwords.
- Create the appropriate vendor account and store/profile records using the existing schema.
- Newly registered vendors must follow the existing Admin approval and mandatory vendor-document verification requirements. Do not automatically grant approved status or bypass verification.
- After registration, show the correct pending-approval or next-step screen.
- Existing vendor login, profiles, products, stock, orders, documents, and sessions must continue working.
- Do not create duplicate vendor profiles if registration is retried.

## 2. Forgot Password — All Portals

Apply a consistent password-reset experience to every applicable portal:
- Customer
- Vendor
- Delivery Partner
- Admin

### Requested user experience
When the user selects **“Forgot Password?”**, show these two fields directly:
- New Password
- Re-enter New Password

Do not ask the user to enter an email address or username on this screen.

### Important security requirements
A user must not be able to change another person's password merely by opening the Forgot Password screen. Before saving the new password, verify account ownership through the project's existing secure authentication or recovery mechanism.

Inspect the current Supabase Auth and username-registry architecture and implement the safest compatible approach:
- Show the requested new-password fields directly on the Forgot Password screen.
- If account verification is required, handle it through an existing valid session, previously verified recovery state, secure recovery code, or another appropriate secure mechanism. Do not silently bypass verification.
- Do not expose whether another user's account exists.
- Do not allow users to change passwords belonging to other roles.
- Validate password strength and ensure both password fields match.
- Display clear success and failure messages.
- Invalidate or refresh sessions appropriately after a password change, according to the existing security design.
- Preserve existing login methods, role-based authorization, username mappings, Admin authentication, and session persistence.

**Do not implement an insecure direct password change just to eliminate the email/username field.** If the current architecture cannot safely support this exact experience, explain the limitation and implement the closest secure flow without weakening authentication.

## 3. Admin Portal — Application Logo Management

Add a new **“Application Branding”** or **“App Logo”** section inside the existing Admin portal.

### Admin functionality
- Upload a new application logo.
- Preview the selected logo before saving.
- Replace the existing logo.
- Display the currently active logo.
- Show clear upload, validation, and save-status messages.

### Logo validation
- Accept suitable image formats such as PNG, JPEG, and SVG only if SVG uploads are safely sanitized and supported.
- Validate file type and file size on the server as well as the client.
- Provide a sensible maximum upload size.
- Preserve aspect ratio and avoid stretching the image.
- Show a fallback logo if no custom logo has been configured.

### Application-wide display
The saved logo should update consistently across the appropriate application branding locations, including:
- Customer portal
- Vendor portal
- Delivery Partner portal
- Admin portal
- Login and registration screens
- Relevant application headers and navigation areas

Use a shared branding configuration or existing application-settings mechanism rather than maintaining separate hardcoded logos in individual portals.

### Security and data handling
- Only an authenticated Admin with the existing server-verified ADMIN role may upload, replace, or update the logo.
- Vendor, Customer, and Delivery Partner users must not be able to modify application branding.
- Store the image using the project's existing appropriate storage mechanism, preferably Supabase Storage if compatible with the current architecture.
- Do not expose Supabase service-role keys or other privileged credentials in frontend code.
- Avoid adding unnecessary database tables or storage buckets if an existing suitable mechanism can be reused.
- Do not alter vendor product images or other uploaded documents.
