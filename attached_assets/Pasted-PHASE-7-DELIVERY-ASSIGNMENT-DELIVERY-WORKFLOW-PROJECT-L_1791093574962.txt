--------------------------------------------------

The existing order lifecycle is:

PLACED
→ ACCEPTED
→ PREPARING
→ READY
→ OUT_FOR_DELIVERY

The order remains the authoritative business object.

5. VENDOR CAN ASSIGN ONLY READY ORDERS
--------------------------------------------------

A vendor may assign a Delivery Partner only when:

order status = READY

The vendor must NOT be able to assign a partner while order is:

PLACED
ACCEPTED
PREPARING
REJECTED
CANCELLED
DELIVERED

If the order is not READY:

return a clear validation error.

Example:

"Delivery partner can only be assigned after the order is marked Ready."

--------------------------------------------------
7. ELIGIBLE PARTNERS
--------------------------------------------------

Only ACTIVE Delivery Partners can be assigned.

INACTIVE partners must not appear as assignable.

Do not allow assigning:

- customer
- vendor
- admin
- inactive partner
- nonexistent partner

The server must validate role and status even if the frontend filters the list.

--------------------------------------------------
8. VENDOR AUTHORIZATION
--------------------------------------------------

A vendor may assign only orders belonging to the vendor's own store.

Vendor A must NOT be able to assign a Delivery Partner to:

- Vendor B's order
- another store's order

Never trust:

storeId
vendorId
partnerId

from the client without server-side authorization.

Resolve ownership from authenticated identity and database relationships.

--------------------------------------------------
9. ASSIGNMENT CREATION
--------------------------------------------------

When the vendor assigns a partner:

1. Verify vendor owns the order/store.
2. Verify order status = READY.
3. Verify partner exists.
4. Verify partner role = DELIVERY_PARTNER.
5. Verify partner status = ACTIVE.
6. Verify no conflicting active assignment exists.
7. Create/update assignment transactionally.
8. Record assignment timestamp.
9. Make the assignment visible in the partner portal.

Do not create duplicate active assignments.

--------------------------------------------------
10. REASSIGNMENT
--------------------------------------------------

Do not allow arbitrary reassignment while a partner is actively handling an order.

Recommended rule:

If assignment is:

PENDING

vendor may change the assigned partner.

If assignment is:

ACCEPTED
PICKED_UP
OUT_FOR_DELIVERY

vendor must NOT silently replace the partner.

If reassignment is genuinely required later, it must be an explicit workflow.

Do not create a complex reassignment system in this phase.

--------------------------------------------------
14. PARTNER ACCEPT DUTY
--------------------------------------------------

For:

assignment status = PENDING

show:

[ Accept Duty ]
[ Reject Duty ]

Accepting:

PENDING
→ ACCEPTED

Record accepted_at.

Server must verify:

- authenticated user is DELIVERY_PARTNER
- partner is ACTIVE
- assignment belongs to authenticated partner
- assignment is still PENDING
- order is still eligible

Do not allow a partner to accept another partner's assignment.

--------------------------------------------------
15. PARTNER REJECT DUTY
--------------------------------------------------

For:

assignment status = PENDING

allow:

[ Reject Duty ]

Before rejection, show a confirmation.

Optional rejection reason may be supported if the existing architecture already has a suitable field.

On rejection:

PENDING
→ REJECTED

Record rejected_at.

The order itself must NOT automatically become REJECTED.

IMPORTANT:

Delivery assignment rejection is NOT the same as customer/vendor order rejection.

The vendor's READY order remains READY and can later be assigned appropriately.

Do not silently cancel the customer order.

--------------------------------------------------
16. REASSIGN AFTER PARTNER REJECTION
--------------------------------------------------

After a partner rejects the assignment:

- assignment becomes REJECTED
- vendor sees that assignment was rejected
- order remains READY
- vendor can assign another ACTIVE Delivery Partner

Do not automatically choose another partner.

Do not auto-assign.

--------------------------------------------------
17. PICKUP
--------------------------------------------------

After:

assignment = ACCEPTED

Partner should see:

[ Mark Picked Up ]

Do not allow pickup before acceptance.

On pickup:

assignment:
ACCEPTED
→ PICKED_UP

Record picked_up_at.

At this point the order should remain operationally consistent with the existing lifecycle.

Do not immediately mark DELIVERED.

--------------------------------------------------
18. OUT FOR DELIVERY
--------------------------------------------------

After pickup, allow:

[ Start Delivery ]

or equivalent clear action.

Transition:

assignment:
PICKED_UP
→ OUT_FOR_DELIVERY

order:
READY
→ OUT_FOR_DELIVERY

Both changes must happen transactionally.

Only the assigned active Delivery Partner may perform this action.

Vendor must not be able to arbitrarily mark an order OUT_FOR_DELIVERY through a client-side status override.

Use existing legal order-transition mechanisms.

--------------------------------------------------
19. DELIVERED
--------------------------------------------------

For:

assignment = OUT_FOR_DELIVERY

show:

[ Mark Delivered ]

On successful completion:

assignment:
OUT_FOR_DELIVERY
→ DELIVERED

order:
OUT_FOR_DELIVERY
→ DELIVERED

Record delivered_at.

Both must happen transactionally.

Only the assigned Delivery Partner may complete delivery.

Do not allow:

- customer to mark delivered
- unrelated vendor to mark delivered
- another delivery partner to mark delivered

25. CANCELLATION / REJECTION INTERACTION
--------------------------------------------------

Respect the existing order cancellation rules.

Do not invent new customer cancellation behavior.

If an order is already:

OUT_FOR_DELIVERY
or
DELIVERED

do not allow ordinary customer cancellation.

If a delivery assignment is rejected:

- assignment becomes REJECTED
- order remains READY
- vendor can assign another partner

Do not mark the order REJECTED.

--------------------------------------------------
26. CONCURRENCY / DOUBLE ACTIONS
--------------------------------------------------

All delivery actions must be server-side transactional and state-checked.

Examples:

Partner double-clicks Accept Duty.

Expected:
- one successful transition
- no duplicate acceptance

Two requests attempt pickup.

Expected:
- only one succeeds

Partner A attempts to accept Partner B's assignment.

Expected:
- authorization failure

Partner tries to mark a DELIVERED assignment as delivered again.

Expected:
- rejected safely
- no duplicate status/history event

Vendor tries to assign two partners simultaneously.

Expected:
- only one active assignment exists

Use database constraints/transactional checks where necessary.

27. ASSIGNMENT OWNERSHIP
--------------------------------------------------

Every partner operation must resolve:

authenticated user
→ delivery partner profile
→ assignment ownership

Never accept:

partnerId

as proof of authorization.

The server must determine the partner from the authenticated session.

--------------------------------------------------
28. CUSTOMER/VENDOR/PARTNER ROLE ISOLATION
--------------------------------------------------

CUSTOMER:

Can:
- view own orders
- view own delivery status

Cannot:
- assign partners
- accept duties
- pickup
- start delivery
- mark delivered

VENDOR:

Can:
- view own store orders
- assign active partners to own READY orders
- view assignment progress

Cannot:
- accept partner duty
- pickup
- mark delivery complete as partner

DELIVERY_PARTNER:

Can:
- view own assignments
- accept own pending assignment
- reject own pending assignment
- pickup own accepted assignment
- start delivery for own picked-up assignment
- mark own out-for-delivery assignment delivered

Cannot:
- access another partner's assignments
- access vendor management
- access customer management
- assign themselves to arbitrary orders
- manipulate stock

ADMIN:

Existing backend administrative capabilities remain unchanged.

Do not build an Admin Portal.
