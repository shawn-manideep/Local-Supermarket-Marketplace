3. AUTHENTICATION
==================================================

Integrate the customer app with the existing Supabase Auth foundation.

Use Supabase Auth.

Do NOT implement custom:

- password hashing
- JWT generation

- session token generation
- authentication provider
- password storage

Use Supabase Auth as the authentication authority.

The customer application should support:

- sign up
- sign in
- sign out
- authenticated session restoration
- session-aware navigation
- authentication error handling

New public Auth users default to the application role:

customer

Do NOT create any customer-side role assignment mechanism.

Do NOT allow the customer client to choose:

- vendor
- admin

as a role.

The client must never be able to elevate its own role.

5. SESSION MANAGEMENT
==================================================

Implement a reliable customer session foundation.

The app should:

- restore an existing Supabase Auth session when launched
- show an appropriate loading state while determining session state
- route unauthenticated users to authentication screens
- route authenticated users to the protected customer application
- support sign out
- react appropriately when the Auth session changes

Avoid unnecessary repeated session lookups.

Do not store passwords locally.

Do not implement custom token persistence.

Use the Supabase Auth session mechanism.

==================================================
13. CUSTOMER API
==================================================

Create only the backend APIs necessary for Phase 5.

Potential API capabilities:

Customer profile:
- GET own profile
- PATCH own profile

Customer addresses:
- GET own addresses
- GET own address
- POST own address
- PATCH own address
- DELETE own address if safe and supported

Every customer endpoint must:

1. Require authentication.
2. Resolve the authenticated customer identity.
3. Scope access to that customer.
4. Reject attempts to access another customer's resources.
5. Validate input using Zod.
6. Persist using Drizzle.
7. Respect RLS.

Do NOT accept customer_id from the client as the authorization source.

Do NOT allow:

GET /api/customers/:arbitraryCustomerId

to become a way to access another customer.

Prefer authenticated-user-derived identity.

==================================================
14. CUSTOMER ADDRESS SECURITY
==================================================

A customer must only access their own addresses.

Example:

Customer A
  ↓
authenticated Supabase user
  ↓
customer A profile
  ↓
customer A addresses

Customer A must never be able to access:

Customer B's addresses

by changing an ID in the request.

The backend must verify ownership.

RLS must remain enabled.

Do not weaken RLS to simplify development.

==================================================
15. DELETE ADDRESS RULE
==================================================

If address deletion is implemented:

- it must delete/deactivate only the customer's reusable address
- it must NOT affect historical order snapshots
- it must NOT cascade into orders
- it must NOT remove historical delivery information

Historical order data is immutable.

If the existing schema makes hard deletion unsafe, use the safest minimal approach compatible with the current architecture.

Do not redesign the order system in Phase 5.
