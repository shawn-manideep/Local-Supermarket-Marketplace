1. PHASE 10 OBJECTIVE
==================================================

Operationalize the MVP vendor-owned delivery model.

The MVP delivery model is:

delivery_type = vendor_staff

The supermarket/vendor is responsible for delivery using its own staff.

The existing order lifecycle remains authoritative:

READY
  ↓
OUT_FOR_DELIVERY
  ↓
DELIVERED

Do not create a separate delivery lifecycle.

Do not create a separate delivery order.

Do not create a delivery partner system.

==================================================

==================================================

- delivery_type
- delivery_contact_name
- delivery_contact_phone

- vendor_staff
- platform_partner

For MVP:

vendor_staff

platform_partner remains future extensibility only.

Do not implement platform_partner operational functionality.

==================================================
3. VENDOR DELIVERY WORKFLOW
==================================================

The vendor workflow is:

ORDER READY
    ↓
Vendor prepares delivery
    ↓
Vendor marks OUT_FOR_DELIVERY
    ↓
Vendor delivers order
    ↓
Vendor marks DELIVERED

Use the existing Phase 9 lifecycle action mechanism.

Do not create a second status mechanism.

Do not directly modify order status from the UI.

==================================================
4. DELIVERY ACTION
==================================================

When an order is:

READY

the vendor may perform:

OUT_FOR_DELIVERY

When an order is:

OUT_FOR_DELIVERY

the vendor may perform:

DELIVERED

These are already valid Phase 8/9 transitions.

Do not change the transition rules.

27. CONCURRENCY
==================================================

Preserve Phase 8/9 locking behavior.

Example:

Vendor A sees:

READY

Vendor B changes:

READY → OUT_FOR_DELIVERY

Vendor A then attempts:

READY → OUT_FOR_DELIVERY

The second action must not create duplicate history or corrupt state.

Likewise:

OUT_FOR_DELIVERY → DELIVERED

must be protected against duplicate concurrent actions.

Do not introduce a new locking mechanism.
