==================================================
1. PHASE 4 OBJECTIVE
==================================================

Build the store-owned category and product management foundation.

The application MUST use the locked product architecture:

Store
  ├── Category
  │     ├── Product
  │     └── Product
  ├── Category
  │     └── Product
  └── Category
        └── Product

IMPORTANT:

Each supermarket owns its own independent category and product records.

There is NO global product master.

There is NO shared product entity.

There is NO `store_products` table.

Do NOT introduce either of these concepts.

If Store A and Store B both sell "Tata Salt", they have two independent product records belonging to their respective stores.

- store_id

- display/order position if already supported

Do NOT create shared categories across stores.

==================================================
4. CATEGORY FUNCTIONALITY — VENDOR
==================================================

Authenticated vendors must be able to manage categories belonging to their own store.

Implement:

- list own categories
- get category details
- create category
- update category
- activate category
- deactivate category

All operations must be restricted to the authenticated vendor's store.

Vendor A must never be able to:

- read Vendor B's categories
- modify Vendor B's categories
- deactivate Vendor B's categories
- create a category under Vendor B's store

Do not trust request-body `store_id`.

The backend must derive the store from the authenticated vendor.

==================================================
5. CATEGORY VALIDATION
==================================================

Use Zod for request validation.

Validate appropriate fields such as:

- name
- description
- display/order position if supported

Reject:

- empty category names
- invalid values
- malformed requests
- unauthorized store references

Do not introduce unnecessary business restrictions such as arbitrary limits unless required by the existing architecture.

==================================================
6. CATEGORY DEACTIVATION / DELETE RULE
==================================================

Categories must NOT be hard-deleted once they can be historically referenced.

Use:

is_active

for catalog lifecycle.

Meaning:

is_active = true
→ active/customer-facing category

is_active = false
→ disabled/not customer-facing

Do not confuse deactivation with temporary product availability.

If a category has products, deactivation must not destroy those products.

Do not implement cascading hard deletion.

==================================================

Reuse the existing Phase 2 `products` table.

Products are store-owned.

Each product must belong to:

- exactly one store
- optionally one category belonging to that same store

The existing product architecture includes:

- id
- store_id
- category_id
- name
- description
- sku
- external_code
- price
- availability
- stock_quantity
- image_url
- is_active
- created_at
- updated_at

Preserve the existing schema rather than unnecessarily redesigning it.

==================================================
8. PRODUCT IDENTITY RULE
==================================================

SKU and external_code are optional.

They may initially be NULL.

Product names are NOT permanent identifiers.

Do NOT create a global uniqueness rule such as:

UNIQUE(name)

across all stores.

Do NOT assume products with the same name are the same product.

If uniqueness constraints already exist, inspect them and preserve only those compatible with the locked architecture.

==================================================
9. PRODUCT CATEGORY OWNERSHIP
==================================================

A product's category must belong to the SAME store as the product.

For example:

Store A
  Category A1
    Product A1

Store B
  Category B1
    Product B1

Product A1 must never be assignable to Category B1.

Enforce this in backend validation and, where appropriate, database constraints.

Never rely only on the client UI.

==================================================
11. CRITICAL PRODUCT LIFECYCLE RULE
==================================================

There are TWO separate concepts:

A. is_active

B. availability

They MUST remain separate.

`is_active = false`

means:

- disabled
- discontinued
- not customer-facing

`availability = false`

means:

- product remains active
- product temporarily cannot be ordered/sold

Example:

Product:
is_active = true
availability = false

means:

"The product still exists in the store catalog but is currently unavailable."

Do NOT automatically set is_active=false when availability=false.

Do NOT delete a product merely because it is unavailable.

==================================================
12. PRODUCT HARD DELETE
==================================================

Products must NOT be hard-deleted because historical orders may reference them.

Use:

is_active

for catalog deactivation.

Historical order records must remain intact.

Do not create a DELETE endpoint that physically removes products.

If an existing generic DELETE implementation exists, replace it with safe deactivation behavior only where necessary.

Do not break historical order relationships.

19. SECURITY / TENANT ISOLATION
==================================================

Security is mandatory.

Vendor A must only access:

Store A
  ↓
Store A categories
  ↓
Store A products

Vendor A must NEVER access Store B by modifying:

- store_id
- category_id
- product_id

in a request.

The backend must verify relationships.

For example, when Vendor A assigns a product to Category B:

1. Authenticate vendor
2. Resolve Vendor A's store
3. Verify Category B belongs to Vendor A's store
4. Reject if it does not
5. Persist only valid relationships

Do not rely on the frontend.

Preserve Phase 2 RLS.

Do not weaken RLS to make development easier.
