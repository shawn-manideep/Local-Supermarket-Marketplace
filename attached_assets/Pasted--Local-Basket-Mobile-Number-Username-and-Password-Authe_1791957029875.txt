# Local Basket — Mobile Number Username and Password Authentication UI

Update the authentication experience in the Customer, Vendor, and Delivery Partner portals.

First inspect the existing authentication architecture, account identity mapping, registration flows, password recovery implementation, and role-based authorization. Reuse the existing backend and Supabase authentication mechanisms wherever possible.

## 1. Login Page Changes — All Three Portals

Apply consistent changes to:
- Customer portal
- Vendor portal
- Delivery Partner portal

### Login form
Replace the existing “Username or Email” field with:

**Label:** Mobile Number  
**Placeholder:** Enter your registered mobile number

Keep the Password field and existing password visibility control.

Requirements:
- Remove email-based login inputs and email-login wording from these three login screens.
- Accept a registered mobile number as the login identifier.
- Normalize Indian mobile numbers consistently, supporting an optional `+91` country code and appropriate validation.
- Look up the mobile number through a secure backend authentication flow and authenticate the correct existing account.
- Do not treat a mobile number as a verified identity unless ownership has been established.
- Preserve existing account UUIDs, usernames, stores, orders, delivery assignments, account status, and role mappings.
- Do not create replacement Auth users or automatically merge accounts.
- Do not allow a Customer to log in as a Vendor or Delivery Partner by manipulating the request.
- Keep Admin authentication and its existing email/password login unchanged.

### Existing account compatibility
Inspect how current accounts are identified. If mobile numbers are not yet stored or verified for every account, do not silently substitute an address recipient number, order contact number, or arbitrary contact field as the login identity.

Provide a safe, backward-compatible approach for existing users who do not yet have a verified mobile number. Do not lock them out or invent verified phone numbers.

## 2. Forgot Password — All Three Portals

Replace the current Forgot Password screen's email/username-entry presentation with the following requested interface:

**New Password**
- Password input with an appropriate visibility toggle.

**Re-enter Password**
- Password confirmation input with an appropriate visibility toggle.

**Button:** Save Password

Requirements:
- Show these fields directly when the user selects “Forgot Password?”
- Do not ask for an email address or username on this screen.
- Validate password strength and reject mismatched passwords.
- Display clear success and failure messages.
- Return the user to the relevant login page after a successful password reset.
- Do not modify the password until account ownership has been securely verified.

### Mandatory security behavior
The interface must not enable an unauthenticated person to reset another user's password just by entering a mobile number or opening the page.

Inspect the existing Supabase Auth and backend recovery architecture. Use a valid existing authenticated session, a previously verified recovery state, or another supported secure recovery mechanism.

If secure ownership verification cannot be completed with the requested two-field screen alone, keep the two password fields visible but require the necessary verification before allowing the save operation. Do not bypass Supabase Auth or create an insecure direct password-update endpoint.

Preserve Admin's existing recovery behavior.

## 3. Registration Pages — No Email Input

- Remove email as a required user-facing registration field for Customer and Vendor if the current architecture can safely support this change.
- Do not introduce public Delivery Partner self-registration; retain existing Admin provisioning and activation controls.
- Use mobile number as the intended login identifier.
- Require mobile-number ownership verification before treating the number as a trusted login identity.
- Do not create duplicate users or profiles.
- Preserve Vendor approval, mandatory document verification, Customer account status, and Delivery Partner active/inactive restrictions.
- Do not assume that removing an email field from the UI eliminates any underlying Supabase Auth email requirement. Resolve the actual account-creation and recovery requirements safely before changing the registration flow.
- Keep Admin registration/login and email/password authentication unchanged.
