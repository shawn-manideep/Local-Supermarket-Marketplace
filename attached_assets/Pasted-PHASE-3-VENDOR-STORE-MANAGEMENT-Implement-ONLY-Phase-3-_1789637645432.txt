==================================================
3. STORE MANAGEMENT — VENDOR
==================================================

Create the required backend functionality for an authenticated vendor to access and manage their own store.

Vendor must be able to:

GET their own store.

UPDATE permitted store information.

Permitted vendor-editable fields should be limited to appropriate operational/profile information such as:

- name
- description
- logo_url/image_url if already represented in schema
- phone
- delivery_fee
- min_order_value

Do NOT allow the vendor to update:

- id
- owner_user_id
- status
- commission_rate
- created_at
- updated_at through arbitrary client control

The backend must derive the vendor's store from the authenticated identity.

Do not accept store_id as an authorization mechanism.

If a route includes a store identifier for resource addressing, it must still verify ownership server-side. Prefer deriving the store from the authenticated vendor identity where practical.

==================================================
4. STORE STATUS
==================================================

Existing store statuses:

- PENDING_APPROVAL
- ACTIVE
- SUSPENDED
- REJECTED

Vendor must be able to view their current store status.

Vendor must NOT be able to change:

- approval status
- suspension status
- rejection status

Only authorized admin functionality may change store status.

Do not introduce additional statuses.

==================================================
5. VENDOR SERVICE PINCODES
==================================================

Implement vendor management for:

store_service_pincodes

Vendor must be able to:

- list their service pincodes
- add a service pincode
- remove a service pincode

All operations must be scoped to the authenticated vendor's own store.

Validate pincode format appropriately for the application's India-first MVP.

Do not introduce maps, GPS, geolocation, delivery-radius calculations, or location services.

Do not allow one vendor to manipulate another store's pincodes.

Do not create duplicate pincodes for the same store.

==================================================
6. STORE OPERATING HOURS
==================================================

Implement vendor management for:

store_operating_hours

Vendor must be able to:

- view operating hours
- create/update operating hours
- configure the store's weekly schedule

Preserve the existing schema.

If the schema supports day-of-week and opening/closing times, validate:

- valid day
- valid time format
- opening time
- closing time
- closed-day representation if supported by the existing schema

Do not implement customer store discovery yet.

Do not build complex holiday/calendar management.

Do not introduce timezone complexity beyond the existing architecture.

==================================================
7. ADMIN STORE MANAGEMENT
==================================================

Implement protected admin functionality for store management.

Admin must be able to:

- list stores
- view store details
- approve a pending store
- reject a pending store
- suspend an active store
- change a suspended store back to ACTIVE when appropriate
- manage the store commission rate

Admin-only actions must require:

1. authenticated Supabase user
2. application role = admin
3. backend authorization
4. database/RLS authorization

Do NOT expose admin functionality to customers or vendors.

==================================================
8. COMMISSION MANAGEMENT
==================================================

The Phase 2 architecture established:

stores.commission_rate

Requirements:

- nullable
- range validated according to existing schema
- vendor cannot modify it
- admin may set/update it
- order commission snapshots remain historical and immutable

For Phase 3, implement only the ability for an authorized admin to manage the store-specific commission rate.

Do NOT implement:

- automated settlements
- payouts
- payment processing
- invoices
- financial reconciliation
- commission reports

The effective-rate calculation for future orders must remain compatible with:

store-specific commission_rate
OR platform default when store commission is null.

Do not create a platform settlement system.

==================================================
9. STORE STATUS TRANSITIONS
==================================================

Enforce reasonable backend state transitions.

At minimum:

PENDING_APPROVAL → ACTIVE
PENDING_APPROVAL → REJECTED
ACTIVE → SUSPENDED
SUSPENDED → ACTIVE

Do not allow vendors to perform these transitions.

Do not silently permit arbitrary status changes through generic update endpoints.

If the existing architecture does not yet include a status-history table, do not invent a large new audit subsystem in this phase unless required for correctness.

12. SECURITY
==================================================

Security is a primary requirement.

Vendor isolation must remain:

authenticated vendor
→ resolve own store
→ scope query by store_id
→ verify ownership
→ database/RLS enforcement

Never:

authenticated vendor
→ trust request.body.store_id

Prevent:

- cross-store reads
- cross-store updates
- cross-store deletes
- vendor commission modification
- vendor status modification
- owner reassignment
- role escalation

Admin endpoints must require admin role.

Customer users must not access vendor/admin management endpoints.

Do not expose service-role credentials to client code.
