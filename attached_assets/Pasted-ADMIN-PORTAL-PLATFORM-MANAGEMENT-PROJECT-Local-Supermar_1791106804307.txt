ADMIN PORTAL — PLATFORM MANAGEMENT

PROJECT:
Local Supermarket Marketplace

OBJECTIVE:
Implement a dedicated Admin Portal for platform-level management of:

1. Vendors
2. Customers
3. Delivery Partners

The Admin Portal must use the existing ADMIN role and existing authentication architecture.

IMPORTANT:
The application currently has:

- Customer Portal
- Vendor Portal
- Delivery Partner Portal
- Backend ADMIN role/authentication

There is currently NO Admin Portal UI.

Create the Admin Portal now.

This is a platform-management portal, NOT a replacement for the existing Vendor, Customer, or Delivery Partner portals.

--------------------------------------------------
1. SCOPE
--------------------------------------------------

IMPLEMENT:

- Admin login/access
- Admin dashboard
- Vendor management
- Customer management
- Delivery Partner management
- Account status management
- Vendor/store approval management
- Partner provisioning
- Basic search/filtering
- Account detail views
- Safe account activation/deactivation
- Appropriate auditability
- Role-based authorization
- Responsive Admin UI

DO NOT IMPLEMENT:

- Customer shopping
- Vendor product management
- Master Catalog management unless already supported by a separate approved admin capability
- Stock management
- Order fulfillment
- Delivery execution
- GPS
- Maps
- Payments
- Financial settlement
- Vendor payouts
- Customer password viewing
- Partner password viewing
- Password storage
- Role self-service changes
- Admin self-registration

--------------------------------------------------
2. ADMIN AUTHENTICATION
--------------------------------------------------

Use the existing ADMIN authentication architecture.

The existing admin authentication is email/password through the established Supabase Auth mechanism.

DO NOT replace it with username/password.

DO NOT create a second authentication system.

Admin login:

Email
+
Password

After successful authentication:

- resolve the application role
- verify ADMIN role server-side
- route to Admin Portal

A non-admin user must never gain access by manually navigating to the Admin Portal URL.

--------------------------------------------------
9. VENDOR APPROVAL
--------------------------------------------------

If a vendor/store is:

PENDING_APPROVAL

Admin can:

APPROVE

or

REJECT

Approval should use the existing store status architecture.

Do not create another approval system.

When approved:

PENDING_APPROVAL
→ ACTIVE

When rejected:

PENDING_APPROVAL
→ REJECTED

The exact existing legal transitions must be respected.

Do not bypass backend transition rules.

--------------------------------------------------
10. VENDOR SUSPENSION
--------------------------------------------------

Admin may suspend an active vendor/store where the existing business model permits it.

Example:

ACTIVE
→ SUSPENDED

A suspended vendor must not be able to perform vendor operations that require an active store.

Do not delete vendor data.

Do not delete historical orders.

Do not delete historical product/order snapshots.

--------------------------------------------------
11. VENDOR REACTIVATION
--------------------------------------------------

Admin may reactivate a suspended vendor when permitted.

Example:

SUSPENDED
→ ACTIVE

Reactivation must not:

- recreate deleted data
- modify historical orders
- modify stock unexpectedly
- alter historical snapshots

15. CUSTOMER DEACTIVATION

19. DELIVERY PARTNER USERNAME
--------------------------------------------------

- reserved-name protection

Do NOT create a second username namespace.

--------------------------------------------------
20. DELIVERY PARTNER STATUS
--------------------------------------------------

Use the existing:

ACTIVE
INACTIVE

state.

When inactive:

- partner cannot log in
- existing protected partner APIs must reject access
- partner must not be assignable to new deliveries

When reactivated:

- partner can log in again
- partner becomes eligible for assignment according to existing Phase 7 rules

Do not automatically modify existing delivery assignments when a partner is deactivated.

If the partner has active assignments, show an appropriate warning to the admin rather than silently reassigning or cancelling deliveries.

--------------------------------------------------
21. ACTIVE DELIVERY PARTNER SAFETY
--------------------------------------------------

Before deactivating a Delivery Partner:

Check whether the partner currently has:

- PENDING assignments
- ACCEPTED assignments
- PICKED_UP assignments
- OUT_FOR_DELIVERY assignments

If active assignments exist:

Show a warning.

Do NOT silently:

- cancel orders
- reassign deliveries
- mark deliveries delivered
- alter customer orders

The admin may need a separately designed reassignment workflow later.

For this phase, preserve the existing delivery state safely.

--------------------------------------------------
25. ADMIN AUTHORIZATION
--------------------------------------------------

Every Admin API must verify:

1. authenticated session
2. ADMIN application role

Never trust a client-provided role.

A CUSTOMER cannot call Admin APIs.

A VENDOR cannot call Admin APIs.

A DELIVERY_PARTNER cannot call Admin APIs.

Authorization must be enforced server-side.

Frontend route protection is only a UX layer.

--------------------------------------------------
26. ADMIN SELF-PROTECTION
--------------------------------------------------

Do not implement admin self-registration.

Do not allow an admin to change another user's role arbitrarily through a generic "Change Role" dropdown.

The Admin Portal should manage approved application entities according to their dedicated workflows.

Do NOT create:

Customer → Admin
Vendor → Admin
Partner → Admin

role conversion controls.

Admin accounts remain controlled through the existing secure administrative mechanism.

27. AUDITABILITY
--------------------------------------------------

Administrative actions should be traceable.

At minimum, record appropriate events for:

- vendor approval
- vendor rejection
- vendor suspension
- vendor reactivation
- customer deactivation
- customer reactivation
- delivery partner creation
- delivery partner activation
- delivery partner deactivation
- delivery partner reactivation

Use the smallest appropriate audit mechanism.

If an existing audit/event structure exists, reuse it.

Do NOT build a large enterprise audit subsystem.

At minimum capture where practical:

- admin identity
- action
- target entity
- timestamp

Do not record passwords or secrets.
