==================================================
2. CRITICAL PRODUCT ARCHITECTURE
==================================================

The locked product architecture is:

Store
  ├── Category
  │     ├── Product
  │     └── Product
  └── Category
        └── Product

There is:

NO global product master.

NO `store_products` table.

Each store owns independent product records.

If two stores sell the same product, they remain separate records.

Never attempt to merge products between stores.

Do not create a global product identity layer.

==================================================
3. CUSTOMER STORE DISCOVERY
==================================================

Authenticated customers should be able to discover supermarkets serving their pincode.

Use the customer's saved address pincode.

The customer may also be allowed to select/change the pincode used for discovery if this fits the existing UX, but do not create a separate location/GPS system.

Store eligibility is based on:

1. Store status = ACTIVE
2. Customer pincode exists in store_service_pincodes

Only eligible ACTIVE stores should be customer-visible.

PENDING_APPROVAL stores must NOT appear.

SUSPENDED stores must NOT appear.

REJECTED stores must NOT appear.

Do not expose inactive stores through normal customer discovery APIs.

==================================================
4. PINCODE-BASED MATCHING
==================================================

The MVP uses pincode matching only.

Do NOT implement:

- GPS
- maps
- geolocation
- live location
- delivery radius
- distance calculation
- route calculation
- latitude/longitude
- delivery partner location
- location tracking

A customer's six-digit Indian pincode is the geographic matching key.

Example:

Customer pincode:
500072

Store A:
500072
500073

Store A is eligible.

Store B:
500081

Store B is not eligible.

- GET /api/customer/stores?pincode=:pincode
- GET /api/customer/stores/:storeId
- GET /api/customer/stores/:storeId/categories
- GET /api/customer/stores/:storeId/products
- GET /api/customer/stores/:storeId/products/:productId

Follow the existing API conventions.

Do not blindly use these exact paths if the existing project has a better established convention, but preserve the same semantics.

Every customer marketplace endpoint must:

- require customer authentication where appropriate
- validate inputs
- enforce store visibility rules
- return only customer-visible data
- prevent cross-store product/category access
- respect RLS

Do not trust the client to determine whether a store is customer-visible.

The backend must enforce:

store.status = ACTIVE

and service-pincode eligibility.

12. CATEGORY VISIBILITY
==================================================

==================================================
13. PRODUCT VISIBILITY
==================================================

Customer-facing products should respect:

is_active = true

Products with:

is_active = false

must not appear in the normal customer catalog.

Products with:

is_active = true
availability = false

remain catalog products but are temporarily unavailable.

Do NOT treat unavailable products as deleted.

Do NOT automatically hide unavailable products unless the existing business rules explicitly require it.

Prefer showing the product with a clear:

"Unavailable"

state.

The customer must not be able to treat an unavailable product as available for ordering.

Actual ordering/cart enforcement belongs to later phases.
